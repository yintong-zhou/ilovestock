## Frontend plan (Gon): `JobProgress` with elapsed time and ETA

I read `web/src/components.tsx:110-154`, `types.ts:82-92` and `format.ts`. The component already polls `/api/progress` every second, shows the step text and percent, and hides itself when `r[job]` is `null`. That last point already gives the "block disappears at the end" behaviour. Only the extra fields and their display are new.

**Open point for @forge.** The handoff doesn't say what format `started_at` has. I assume **Unix epoch seconds as a float, non-null while a run is active**, and `eta_seconds` as **seconds, `number | null`**. If Forge uses ISO strings instead, only the `elapsed` line in `JobProgress` changes. The browser and server are on the same machine (127.0.0.1), so clock skew is negligible.

## Phase 1: Contract and formatting helpers
Goal: mirror the backend contract and add pure, testable formatters.
- `web/src/types.ts`: add `started_at: number` and `eta_seconds: number | null` to `Progress`. Update the doc comment: `eta_seconds` is null until it can be estimated, and `started_at` is epoch seconds.
- `web/src/format.ts`: add `duration(seconds: number): string`.
  - Below 60 s it returns `"42s"`.
  - Below 1 h it returns `"3m 05s"`.
  - From 1 h it returns `"1h 02m"`.
  - It clamps negative or non-finite input to `0s`.
- Checks: Vitest tests for `duration` covering 0, 59, 60, 3599, 3600 and negative or NaN input. `npm run lint` and `npm run build` must pass, so `tsc` verifies the type change.

## Phase 2: `JobProgress` UI
Goal: show the step, the counter, the elapsed time and the approximate remaining time.
- Keep the existing polling. Add a `now` state that ticks every second, so the elapsed time advances between polls. It runs only while `step` is non-null, and the cleanup clears it.
- Layout (English labels, existing Tailwind classes):
  - Top row: `step.text` on the left, `pct%` on the right (unchanged).
  - New secondary row below the bar, in small muted text (`text-sm text-nd`, to be checked against the brand tokens).
    - Left: `{done} of {total}` when `total > 0`.
    - Right: `Elapsed {duration(now - started_at)}`, then ` · About {duration(eta_seconds)} left` only when `eta_seconds !== null`. Round the ETA to the nearest 5 s below 1 min so it doesn't flicker.
  - When `total === 0` the pulsing bar stays and the counter is omitted. Elapsed time is still shown.
- Accessibility:
  - The progressbar keeps `aria-valuenow` and `aria-label`.
  - The secondary row is plain text with no `aria-live`, so a screen reader doesn't announce it every second.
  - `aria-valuetext` is set to `"{done} of {total}, about {x} left"` so the estimate is available on demand.
- No frontend rules or estimation logic. The ETA comes only from the server.
- Checks: Vitest plus Testing Library render tests. They would need `@testing-library/react` and `jsdom` as devDependencies, which Vitest alone doesn't cover, so @bolt must confirm them. Without them, extract the label building into a pure function (`progressLabels(step, nowSeconds)`) and test only that. The pure-function route is my default and fits the approved scope.
  - Cases: `total = 0`, `eta_seconds = null`, `eta_seconds` set, and `done = total`.
  - Manual check: run Analysis and Screener against the fake provider via `create_app(...)`. No live Finviz or Yahoo requests.
